# 设备优先的边云协同认证与调度改造方案

本文档描述一种更适合当前项目的改造方案：

- 不再维护普通用户本地账号体系
- 不再手工做 `openwebui_user_id -> 本地用户` 绑定
- 让**边端设备**成为调度主身份
- 让 OpenWebUI 用户只作为“当前使用者”身份存在
- 不影响云端后端现有的：
  - Prometheus 指标采集
  - runtime 定位
  - 切分策略下发
  - 任务状态跟踪

本文档是方案草案，不涉及代码修改。

---

## 0. 与近期已融入代码增强的关系

当前仓库已经融入了一批底层增强，这些增强与本方案**不冲突**，并且应视为后续实施时的现有基础，而不是需要回滚的部分：

- 数据库层增强：
  - `backend/app/db/database.py` 已增加 SQLite `timeout=30`
  - `pool_pre_ping=True`
  - `expire_on_commit=False`
  - `session_scope()`
- 网络探测与 Prometheus 查询模块化：
  - `backend/app/services/network_probe.py`
  - `backend/app/services/prometheus_metrics.py`
  - `schedule.py` 已通过 service 模块调用网络探测与指标采集
- 管理员初始化安全兼容：
  - `backend/app/core/config.py` 已支持 `ADMIN_USERNAME`
  - `ADMIN_PASSWORD`
  - `backend/app/models/models.py` 已优先从环境变量初始化管理员

这些改动不会改变“设备优先 + 普通用户不再依赖本地账号”的总体方向。

它们对本方案的影响主要体现在两点：

1. 后续改代码时要优先复用这些新模块和新配置，不要把逻辑重新堆回旧文件
2. 管理员登录与管理员初始化能力继续保留，不属于本次普通用户认证改造的目标范围

---

## 1. 为什么需要这个方案

你当前系统真正要完成调度，核心依赖的是：

1. 当前是哪台边端设备
2. 当前固定使用哪台云端设备
3. 这台边端和这台云端上有哪些 runtime 正在运行
4. 如何采边端/云端的监控指标
5. 如何把策略下发到边端/云端 runtime

而不是：

- 某个普通用户在本地后端有没有账号
- 某个 OpenWebUI 用户是否已经手工绑定到某个本地用户

当前最复杂、最影响接入体验的点，就是：

- 新边端设备接入时，要先在后端建普通用户
- 新 OpenWebUI 账号接入时，要手工绑定 `openwebui_user_id`
- 用户换一个 OpenWebUI 账号，又要重新改绑定

这个复杂度的根本原因是：

**你现在把“设备识别”和“用户账号体系”耦合在了一起。**

本方案的目标，就是把它们拆开。

---

## 2. 核心设计思想

本方案的核心思想只有一句话：

**调度按设备走，用户只做附加身份。**

也就是说：

- 边端设备是谁，由云端后端根据请求来源 IP 自动匹配
- 当前阶段云端设备固定为本机 `10.144.144.2`（设备 `cloud`）
- OpenWebUI token 只负责说明“当前是谁在使用系统”
- 不再让“本地普通用户账号”承担设备绑定职责

---

## 3. 本方案的总体结构

### 3.1 长期保留

继续保留并作为主数据源：

- `devices`
  - 系统设备资产表
- `model_nodes`
  - runtime 注册表
- `schedule_tasks`
  - 调度任务表

这些表是当前后端实现完整功能所必须的。

### 3.2 不再保留为主流程依赖

普通用户主流程不再依赖：

- 本地普通用户账号
- `openwebui_user_id -> User`
- `users.allowed_devices`

### 3.3 云端前端页面的角色调整

本方案建议进一步收敛一个原则：

**云端前端页面不再给普通用户使用，只保留管理员进入查看设备监控和后台管理。**

这意味着：

- 普通用户不再进入云端前端页面查看设备指标
- 普通用户不再通过云端前端页面查看 Grafana
- 云端前端页面主要承担：
  - 管理员设备资产管理
  - 管理员 Grafana / Prometheus 监控查看
  - 管理员 runtime 状态查看

### 3.4 OpenWebUI 用户的角色

OpenWebUI 用户在本方案中不再是“设备授权主键”，而是：

- 当前请求发起者
- 审计信息来源
- 可选的用户偏好来源

---

## 4. 设备优先方案如何工作

## 4.1 边端设备身份来源

本方案默认采用：

**由云端后端根据请求来源 IP 去匹配 `devices` 表，自动确定当前是哪台边端设备。**

这意味着：

- 后端不再靠用户账号推断边端设备
- 前端不需要知道自己的 `edge_device_id`
- 前端不需要额外发送设备 ID
- 后端在收到请求后，直接根据 `request.client.host` 与 `devices` 表中的边端设备 IP 做匹配

### 4.1.1 识别发生的时间点

边端设备识别不应该等到真正发起调度时才第一次进行。

更合适的做法是：

- 在普通用户第一次进入云端后端的初始化接口时，就完成边端设备识别

推荐把初始化入口统一收敛为：

- `POST /api/v1/session/init`

在这一步里，后端做：

1. 验签 OpenWebUI token
2. 读取 `request.client.host`
3. 在 `devices` 表中匹配边端设备
4. 得到当前会话对应的 `edge_device_id`
5. 创建本次使用的临时会话上下文

### 4.2 云端设备来源

当前阶段不再让边端前端选择云端设备。

云端后端直接固定使用：

- `device_id = cloud`
- `ip = 10.144.144.2`

也就是说，普通用户当前只需要确定：

1. 当前是哪台边端设备
2. 当前要调度哪个模型

云端侧目标暂时由后端固定。

### 4.3 OpenWebUI token 的作用

OpenWebUI token 只负责：

- 验签
- 解析当前用户身份
- 记录当前任务是谁发起的

它不再用于：

- 反查本地普通用户账号
- 决定这次任务允许用哪台边端

---

## 5. 为什么这比“按用户绑定设备”更简单

## 5.1 现在的旧问题

当前模式的问题是：

1. 边端设备变化时，要改本地普通用户配置
2. OpenWebUI 用户变化时，要改本地绑定
3. 用户和设备被绑死，导致接入过程复杂

## 5.2 新模式的简化点

采用设备优先后：

1. 新 OpenWebUI 用户接入，不再需要建本地普通用户账号
2. OpenWebUI 用户换号，不影响边端设备识别
3. 边端设备是谁，由后端按请求来源 IP 自动识别
4. 云端设备当前固定为后端本机设备 `cloud`

也就是说，设备路径和用户路径被分开了：

- 设备负责调度目标
- 用户负责使用者身份

---

## 6. 为什么后端仍然必须保留设备表

虽然本方案不再维护普通用户账号体系，但后端仍然必须保留设备资产表。

原因是后端还要继续做：

1. 根据边端设备拿到 Prometheus 指标目标
2. 根据边端设备找到 runtime 注册信息
3. 根据设备信息下发切分策略
4. 记录每次任务实际用了哪台边端和哪台云端

所以本方案不是“不要设备管理”，而是：

**不要普通用户账号绑定，但保留设备主身份。**

### 6.1 对现有云端前端监控功能的影响

这个方案**不会影响管理员监控功能**。

原因是当前云端前端设备监控/Grafana 的核心依赖仍然是：

- `devices` 设备表
- Prometheus 动态目标发现
- Grafana 内嵌页面

这些都继续保留。

本方案变化的是：

- 普通用户不再通过云端前端页面查看设备监控
- 管理员继续通过云端前端页面查看设备监控

因此可以理解为：

- **管理员监控能力保留**
- **普通用户监控入口收掉**

---

## 7. 本方案依赖请求来源 IP 的成立前提

本方案之所以可以默认使用请求来源 IP 来识别边端设备，是基于一个明确前提：

**真正发起请求的那台设备，就是进行边端推理的那台边端设备。**

也就是说：

- 用户是在边端设备本机上操作
  或
- 边端设备上的服务端代替前端发起请求

在这个前提下，云端后端看到的 `request.client.host` 才能被视为边端设备 IP。

### 7.1 这种方案为什么适合当前项目

对你当前项目来说，这种方式的优点是：

1. 前端负担最小，不需要理解设备 ID
2. 不需要额外维护“前端配置里的边端设备 ID”
3. 后端本来就维护了 `devices` 表，可以直接按 IP 反查设备
4. 后端后续做指标采集、runtime 定位、本来也都是沿着设备 IP 继续往下做

### 7.2 这种方案的边界

但要明确，这种方案只在下列条件成立时可靠：

1. 没有代理、NAT、反向代理改写来源 IP
2. 浏览器或服务端请求的源地址确实就是边端设备本机地址
3. `devices` 表里保存的边端设备 IP 是稳定且准确的

如果未来出现下面这些情况：

- 用户在别的电脑上访问边端页面
- 前端请求经过代理或统一网关
- 请求来源不再等于边端宿主机 IP

那这个方案就需要升级为：

- 显式设备 ID 方案
  或
- 服务端代发方案

也就是说：

**来源 IP 识别是当前阶段最简方案，但不是永久唯一方案。**

## 8. 当前最推荐的接口行为

## 8.1 认证方式

普通用户侧接口直接支持：

```http
Authorization: Bearer <openwebui_token>
```

不再需要：

```http
POST /api/v1/auth/exchange
```

管理员仍然保留：

- 本地 `/api/v1/login`
- 内部 JWT

### 8.1.1 云端前端页面登录策略

在本方案下，云端前端页面只服务管理员，因此建议：

- 云端前端页面继续只认本地管理员登录
- 普通用户不再通过云端前端页面登录
- 普通用户入口统一收敛到边端前端 + OpenWebUI

### 8.1.2 初始化时建立临时会话

本方案推荐在普通用户第一次进入云端后端时，就建立一次临时会话。

这次临时会话的目的，是把一次完整使用流程串起来，包括：

- 边端设备识别
- 固定云端设备绑定
- 模型选择
- 调度任务发起
- 策略加载进度查看
- 切分策略展示

建议的会话内容至少包括：

- `session_id`
- `openwebui_user_id`
- `edge_device_id`
- `edge_ip`
- `cloud_device_id`，固定写为 `cloud`
- `selected_model_type`，可为空
- `created_at`
- `expires_at`

这样前端的一次完整使用，不再依赖每个请求都重新全量推断边端设备。

推荐初始化接口：

```http
POST /api/v1/session/init
Authorization: Bearer <openwebui_token>
```

推荐初始化响应至少返回：

- `openwebui_user_id`
- `session_id`
- 当前识别出的边端设备信息
- 固定云端设备信息（`cloud / 10.144.144.2`）

第一阶段建议直接采用这一种做法：

- `POST /api/v1/session/init` 既负责初始化，也直接把固定云端设备写入会话上下文

这样前端第一次进入后端时不需要再获取或选择云端设备列表。

---

## 8.2 边端设备识别方式

普通用户侧请求不再需要显式带边端设备 ID。

后端处理方式改为：

1. 读取请求来源 IP
2. 在 `devices` 表中匹配对应边端设备
3. 得到当前会话使用的 `edge_device_id`
4. 后续所有 Prometheus 查询、runtime 定位、策略下发都基于这个匹配结果继续进行

也就是说，前端请求只需要带：

```http
Authorization: Bearer <openwebui_token>
```

### 8.2.1 后续请求如何保持同一次使用

本方案不建议每个请求都重新做一次“边端是谁、云端是谁、当前模型是什么”的完整推断。

更合理的方式是：

1. 初始化请求时识别边端设备并创建临时会话
2. 后续请求通过 `session_id` 关联到这次使用
3. 后端继续校验：
   - token 仍属于同一个 OpenWebUI 用户
   - 请求来源 IP 仍与该会话中的 `edge_ip` 一致

也就是说：

- 第一次请求负责“识别并建会话”
- 后续请求负责“续用会话并做一致性校验”

这样可以保证：

- 固定云端设备不会丢
- 模型选择不会丢
- 进度展示、策略展示都属于同一次使用
- 后端能明确知道这整条链路属于哪个边端设备

### 8.2.2 `session_id` 的传递方式

为了减少前端和后端的歧义，本方案建议统一约定：

- 普通用户后续请求统一在请求头里带：

```http
Session-Id: <session_id>
```

适用接口包括：

- `POST /api/v1/schedule/trigger`

这样可以避免：

- 有的接口把 `session_id` 放 body
- 有的接口把 `session_id` 放 query
- 前后端实现不一致

补充说明：

- `Session-Id` 第一阶段主要用于初始化后的会话连续性，以及 `POST /api/v1/schedule/trigger`
- 对已经创建完成的任务查询接口：
  - `GET /api/v1/schedule/tasks/{task_id}`
  - `GET /api/v1/schedule/tasks/{task_id}/strategy`
  - `GET /api/v1/schedule/tasks/{task_id}/stream`
  第一阶段不强制要求继续带 `Session-Id`

这些任务查询接口更适合继续基于：

- `task_id`
- `openwebui_token`

做鉴权与归属校验。

## 8.3 云端设备使用方式

第一阶段建议直接采用：

- `POST /api/v1/session/init` 初始化时就确定当前固定云端设备
- `POST /api/v1/schedule/trigger` 不再提交 `cloud_device_id`

当前固定云端设备为：

- `device_id = cloud`
- `ip = 10.144.144.2`

### `POST /api/v1/schedule/trigger` 请求体

```json
{
  "model_type": "llama-3.2-3b"
}
```

这样第一版最简单：

- 不需要前端展示云端设备选择
- 不需要额外保存长期云端设备偏好
- 每次调度都明确使用同一台本机云端设备

并且建议在第一阶段采用下面的写入方式：

- 初始化时创建 session，同时把 `cloud_device_id` 固定写为 `cloud`
- `model_type` 先留空
- 当前端真正调用 `/api/v1/schedule/trigger` 时：
  - 只提交 `model_type`
- 后端在受理 trigger 时，再把 `model_type` 写入当前 session

如果后面想支持多云端，再把“云端设备选择”作为第二阶段增强项恢复即可。

## 9. 是否还需要保存用户信息

## 9.1 最简版本

可以不维护普通用户本地账号。

只在任务里记录：

- `openwebui_user_id`
- `edge_device_id`
- `cloud_device_id`（固定为 `cloud`）

这样已经足够：

- 审计
- 任务归属
- 基本排障

这里的含义是：

- 不要求有一张“普通用户本地账号表”
- 但调度任务、临时会话、审计记录里仍然可以保留 `openwebui_user_id`

## 9.2 第二阶段推荐版本

建议在第二阶段增强时，再保留一张**轻量用户档案表**，但它不是本地普通用户账号表。

例如：

`openwebui_principals`

只存：

- `openwebui_user_id`
- `status`
- `last_seen_at`
- 可选 `display_name`

用途：

- 记录谁来过系统
- 是否禁用某个 OpenWebUI 用户
- 审计与统计

这比“本地普通用户账号体系”轻得多，也不会再引入手工绑定复杂度。

第一阶段最小闭环里，不强制要求先落这张表。

## 9.3 `users.allowed_devices` 在本方案里的位置

在本方案下，普通用户不再通过云端前端页面查看设备，也不再依赖 `users.allowed_devices` 来决定调度。

因此：

- `users.allowed_devices` 对普通用户主流程不再重要
- 该字段可以逐步收缩为：
  - 管理员兼容字段
  - 历史兼容字段

后续可以考虑逐步把依赖它的普通用户接口收口，例如：

- `/api/v1/users/my_devices`

因为普通用户已经不需要通过云端前端页面查看自己的设备指标。

## 10. 建议的数据模型调整

## 10.1 保留

- `devices`
- `model_nodes`
- `schedule_tasks`
- `users`
  - 仅用于管理员

## 10.2 第二阶段可新增

建议在第二阶段增强时新增一张轻量表：

### `openwebui_principals`

字段建议：

- `id`
- `openwebui_user_id`，唯一
- `display_name`，可选
- `status`
  - `active`
  - `disabled`
- `created_at`
- `updated_at`
- `last_seen_at`

### 是否需要新增用户-设备绑定表

本方案下，**不强制需要**。

因为：

- 边端设备由请求来源 IP 自动匹配得到
- 云端设备当前固定为本机设备 `cloud`

只有当你以后想做：

- 默认云端设备记忆
- 最近使用记录
- 用户偏好

才需要再加轻量绑定/偏好表。

### 10.3 第一阶段建议新增临时会话表

推荐新增一张临时会话表，例如：

### `edge_sessions`

字段建议：

- `id`
- `session_id`，唯一
- `openwebui_user_id`
- `edge_device_id`
- `edge_ip`
- `cloud_device_id`（固定为 `cloud`）
- `model_type`，可为空
- `status`
  - `active`
  - `expired`
  - `closed`
- `created_at`
- `updated_at`
- `expires_at`

这张表不承担长期用户绑定功能，只用于保证“一次完整使用流程”的上下文连续性。

## 11. 调度流程会怎么变化

一次边端使用的推荐流程如下：

1. 边端前端登录 OpenWebUI
2. 前端拿到 `openwebui_token`
3. 前端调用云端后端会话初始化接口，并带：
   - `Authorization: Bearer <openwebui_token>`
4. 云端后端：
   - 验签 OpenWebUI token
   - 解析 `openwebui_user_id`
   - 根据请求来源 IP 匹配边端设备
   - 创建本次使用的临时 session
   - 返回：
     - `session_id`
     - 当前识别出的边端设备信息
     - 固定云端设备信息
5. 前端保存初始化返回的 `session_id`
6. 前端选择：
   - `model_type`
7. 前端发起：
   - `/api/v1/schedule/trigger`
   - 并带 `Session-Id`
8. 后端在受理 trigger 时，把：
   - `model_type`
   写入当前 `session_id`
9. 后端根据当前 `session_id` 中的：
   - `edge_device_id`
   - 固定使用 `cloud`
   完成后续：
   - 指标采集
   - 26 维编码
   - 算法调用
   - 策略下发
   - runtime 进度聚合

---

## 12. 这个方案解决了什么

它直接解决了你现在最头疼的几个问题：

### 1. 新 OpenWebUI 用户接入复杂

解决方式：

- 不再要求创建本地普通用户账号
- 不再要求手工绑定 `openwebui_user_id`

### 2. OpenWebUI 用户换账号后还要改绑定

解决方式：

- 设备识别不再依赖用户账号
- 用户换号不影响边端设备是谁

### 3. 后端完整能力不能丢

解决方式：

- 设备表仍然保留
- runtime 注册仍然保留
- Prometheus 采集仍然按设备走

---

## 13. 这个方案的边界

它不是完全无状态，也不是完全不存任何用户信息。

准确地说：

- **不再维护普通用户账号体系**
- **继续维护设备体系**
- **可选维护轻量 OpenWebUI 用户档案**

这是兼顾“简单接入”和“后端功能完整”的折中方案。

## 14. 对其他协作者的影响

## 14.1 边端前端同学

需要同步：

1. 不再调用 `/api/v1/auth/exchange`
2. 直接使用 OpenWebUI token 调后端
3. 不需要再额外维护或发送边端设备 ID
4. 初始化后保存后端返回的 `session_id`
5. 发起调度时带：
   - `model_type`
6. 第一阶段中，`POST /api/v1/schedule/trigger` 统一带：
   - `Session-Id`

## 14.2 管理端同学

1. 不再维护普通用户账号创建流程
2. 云端前端页面只保留管理员使用
3. 后台管理重点转向：
   - 设备资产
   - OpenWebUI 轻量档案
4. 管理员继续保留：
   - Grafana 监控查看
   - 设备指标查看
   - runtime 状态查看

### 14.2.1 对现有云端前端页面的具体适配建议

建议把当前云端前端页面收敛为：

#### 管理员

- Grafana 内嵌页
- 设备管理

- 设备监控入口
- “我的设备”监控视图
- 普通用户设备指标展示逻辑

也就是说：

**普通用户不再进入云端前端页面，云端前端页面变成管理员专用后台。**

## 14.3 runtime 同学

基本不受影响。

因为本方案不改变：

- `/load_strategy`
- `/runtime_callback/*`
- runtime 注册协议

## 15. 推荐的实施顺序

建议按“两大阶段 + 第一阶段再拆 4 个小阶段”落地。

### 第一步：最小闭环

#### 阶段 1A：认证入口能力

先只改认证入口，不动调度主流程：

1. 普通用户不再走 `/auth/exchange`
2. 普通用户侧接口支持 OpenWebUI token
3. 新增 `POST /api/v1/session/init` 的最小骨架
4. 先跑通：
   - token 验签
   - `openwebui_user_id` 解析
   - 基础返回结构

完成后联调：

- 只测 `POST /api/v1/session/init`
- 确认 OpenWebUI token 能被正确识别

#### 阶段 1B：边端设备识别与临时 session

再补本次使用的上下文：

1. 初始化接口按请求来源 IP 自动匹配边端设备
2. 初始化接口创建临时 session，并返回：
   - `session_id`
   - `openwebui_user_id`
   - 当前识别出的边端设备信息
   - 固定云端设备信息

完成后联调：

- 测 `POST /api/v1/session/init`
- 确认能返回 `session_id`
- 确认能识别边端设备
- 确认错误 IP 会正确报错

#### 阶段 1C：调度主链路切换

再把调度真正切到新路径：

1. 第一阶段中，`Session-Id` 主要用于初始化后的会话连续性，以及 `POST /api/v1/schedule/trigger`
2. `/schedule/trigger` 第一阶段只传 `model_type`
3. `model_type` 在 trigger 受理时写入当前 session
4. 后端按：
   - `edge_device_id`
   - 固定 `cloud_device_id`
   走完整调度链路

完成后联调：

- 跑完整最小链路：
  - `session/init`
  - `trigger`
  - 策略回调
  - runtime 下发
  - 任务完成

#### 阶段 1D：旧链路收口与页面清理

最后再做旧入口收口：

1. 云端前端页面去掉普通用户监控入口，只保留管理员可见
2. 旧普通用户链路改为兼容保留但不再作为主流程
3. 文档与 mock 同步到新流程

完成后联调：

- 验证管理员页面不受影响
- 验证普通用户新链路仍然可用
- 验证旧链路如保留时不会干扰新链路

### 第二步：体验增强项

在第一步稳定后，再补增强能力：

1. 轻量 `openwebui_principals`
2. 多云端设备选择能力
3. 后台对 OpenWebUI 用户的禁用/审计能力
4. 收口 `users.allowed_devices` 在普通用户路径中的历史用途

### 为什么建议这样拆

1. 每次改动的文件和上下文都更小
2. 每一小阶段完成后都能立即联调
3. 出错时更容易定位到底是认证、session 还是调度问题
4. 不需要一次性同时修改认证、session、调度、前端页面全部内容

## 16. 一句话总结

本方案的本质是：

**不再让“普通用户账号”决定调度，而是让“边端设备 + 固定云端设备”决定调度。**

其中：

- 边端设备由后端根据请求来源 IP 自动识别
- 当前阶段云端设备固定为本机 `10.144.144.2`
- OpenWebUI token 只负责说明“是谁在用”
- 一次完整使用通过临时 session 串联
- 云端前端页面只保留管理员监控与管理用途

这是目前最适合你这个项目、同时又能明显降低接入复杂度的方案。
