# 云端后端二阶段资源并发控制代码修改指导文档

本文档用于指导当前云端后端代码，从“按设备对排队”改造成“二阶段资源控制”。

本文档只聚焦当前云端后端**真实负责**的两段工作：

1. 向切分策略计算模块请求切分策略
2. 调用边端 / 云端 runtime 加载切分策略

本文档当前**不处理后续问答会话占用**，也不要求后端去跟踪“模型加载完成后的持续聊天会话生命周期”。

---

## 1. 改造目标

将当前：

- 按 `(edge_device_id, cloud_device_id)` 设备对排队

改造成：

- 第一阶段：全局策略计算串行
- 第二阶段：资源级策略加载排队

同时保证：

- 现有对外接口路径尽量不变
- 现有请求体主结构尽量不变
- 边端前端与算法模块、runtime 模块的基本对接方式不被破坏

---

## 2. 本次改造后的并发模型

### 2.1 第一阶段：策略计算资源

当前假设：

- 切分策略计算模块同一时间只能计算一个切分策略

因此，后端应将其视为：

- 一个全局单资源

规则：

- 任意时刻只允许一个任务进入 `strategy`
- 其余任务进入策略等待队列

### 2.2 第二阶段：策略加载资源

一个任务进入加载阶段时，必须同时占用：

- 对应边端设备的加载资源
- 对应云端设备的加载资源

规则：

- 只有两端加载资源都空闲，任务才允许进入 `loading`
- 否则任务进入加载等待队列

### 2.3 当前阶段的任务完成点

本次改造仍保持：

- 边端加载完成
- 云端加载完成

即视为当前任务完成。

也就是说：

- 加载完成后立即释放当前阶段加载资源
- 先不把后续问答会话占用纳入本次实现

### 2.4 必须保证“放行”是原子的

无论是：

- 新任务进入策略阶段
- 任务从策略阶段进入加载阶段

都不能只做“先查询资源是否空闲，再决定放行”这样的两步松散判断。

否则在两个请求几乎同时进入时，会出现：

- 两个任务都判断资源空闲
- 两个任务同时被放行

因此本次实现必须明确采用以下约束之一：

1. 使用同一个数据库事务完成：
   - 资源占用判断
   - 任务状态更新
2. 或使用单独的调度锁，保证同一时刻只有一个调度推进过程在执行

当前项目是单库 SQLite，第一版更建议采用：

- “短事务 + 明确状态占用判据”的方式

至少要保证：

- 一个任务从 `queued_strategy -> running_strategy`
- 或从 `queued_loading -> running_loading`

这一步对数据库来说是原子的。

## 4. 当前代码中的主要问题

### 4.1 当前排队入口问题

当前 `schedule.py` 在触发任务时，会调用：

- `find_active_task_for_device_pair`
- `count_queued_tasks_for_device_pair`

并据此决定：

- 是否直接开始任务
- 是否把任务标记为 `queued`

问题在于：

- 这套逻辑是“设备对级”
- 不是“资源级”

### 4.2 当前 `queue_len` 语义问题

当前发给算法模块的：

- `edge.metrics.queue_len`
- `cloud.metrics.queue_len`

来自“设备对排队长度”。

这与当前要改造的资源级并发控制不一致，因此后续不能继续沿用该语义。

### 4.3 当前自动推进逻辑问题

当前失败或完成后，推进的是：

- 同一设备对里的下一个任务

而新方案要求推进的是：

- 策略阶段的全局等待任务
- 加载阶段的资源可执行任务

因此原有自动推进逻辑必须重写。

## 5. 建议的状态模型

### 5.1 内部建议状态

建议把当前内部任务阶段重新明确为：

1. `queued_strategy`
   - 等待进入策略计算
2. `strategy`
   - 正在计算切分策略
3. `queued_loading`
   - 策略已生成，等待加载资源
4. `loading`
   - 正在加载切分策略
5. `completed`
   - 当前阶段完成
6. `failed`
   - 当前阶段失败

### 5.2 对外兼容建议

为避免影响现有边端前端展示，建议对外先继续使用现有 `phase` 语义：

- `strategy`
- `loading`
- `completed`

其中：

- `queued_strategy` 对外可映射为：
  - `phase="strategy"`
  - `message="等待进入切分策略计算队列"`
- `queued_loading` 对外可映射为：
  - `phase="loading"`
  - `message="切分策略已生成，等待边云加载资源"`

这样可以不改变主接口结构，只细化文案与内部状态。

## 6. 数据层建议

### 6.1 `ScheduleTask` 建议保留字段

当前建议保留并继续使用：

- `status`
- `phase`
- `phase_progress`
- `overall_progress`
- `message`
- `queue_status`
- `queue_position`
- `dispatched_at`
- `edge_device_id`
- `cloud_device_id`

### 6.2 `queue_status` 建议重定义

当前 `queue_status` 不应再表示：

- 设备对级的 `queued/running`

建议改为更明确的内部阶段状态，例如：

- `queued_strategy`
- `running_strategy`
- `queued_loading`
- `running_loading`
- `completed`

如果你希望保守一些，也可以先保留旧字段名，但重定义取值和注释。

### 6.3 是否新增字段

当前阶段不强制新增数据库字段。

如果想减少改造范围，可以先利用：

- `phase`
- `queue_status`
- `queue_position`

完成第一版逻辑。

只有在后续需要更细粒度统计时，再考虑新增：

- `strategy_queued_at`
- `loading_queued_at`
- `resource_lock_key`

### 6.4 第一版必须明确状态判据

即使当前阶段不新增数据库字段，也必须在实现时明确规定：

- 哪些 `queue_status` 代表“已占用策略资源”
- 哪些 `queue_status` 代表“已占用加载资源”

建议第一版直接固定为：

- `running_strategy`
  - 表示已占用全局策略计算资源
- `running_loading`
  - 表示已占用边云加载资源

这样后续所有资源判断函数都只围绕这两个状态做判定，避免把：

- `phase`
- `message`
- `progress`

误当成资源占用依据。

## 7. 服务层改造建议

### 7.1 替换 `schedule_queue.py` 的职责

当前 `schedule_queue.py` 的核心函数是围绕“设备对”设计的，例如：

- `find_active_task_for_device_pair`
- `count_queued_tasks_for_device_pair`
- `recalculate_queue_positions_for_device_pair`

建议改造成围绕两个阶段：

#### 策略阶段函数

- `find_running_strategy_task(db) -> ScheduleTask | None`
- `count_queued_strategy_tasks(db) -> int`
- `recalculate_strategy_queue_positions(db) -> None`
- `promote_next_strategy_task(db) -> ScheduleTask | None`

#### 加载阶段函数

- `is_loading_resource_available(db, edge_device_id, cloud_device_id) -> bool`
- `count_queued_loading_tasks_for_resources(...)`
- `recalculate_loading_queue_positions(db) -> None`
- `find_next_loadable_task(db) -> ScheduleTask | None`
- `promote_next_loading_task(db) -> ScheduleTask | None`

### 7.2 资源判断建议

当前加载资源判断建议直接基于运行中任务查询：

- 是否已有任务在 `loading`
- 且占用了相同 `edge_device_id`
- 或相同 `cloud_device_id`

只要命中任意一项，就认为资源不可用。

也就是说，加载阶段的互斥关系应为：

- 同边端设备互斥
- 同云端设备互斥

不是“同设备对互斥”。

### 7.3 加载队列是否允许插队，必须先定清楚

本次方案需要明确一个实现选择：

#### 方案 A：严格 FIFO

规则：

- 只检查加载队列队首任务
- 如果队首任务资源还不可用，则后面的任务也不能先执行

优点：

- 用户理解简单
- `queue_position` 语义稳定

缺点：

- 可能降低吞吐
- 容易出现“前面一个任务卡住，后面全被堵住”

#### 方案 B：资源可执行优先

规则：

- 从 `queued_loading` 中按顺序扫描
- 找到第一条资源已满足的任务就先放行

优点：

- 吞吐更高
- 不容易因为一个任务占住特定资源而阻塞全部队列

缺点：

- 不是严格 FIFO
- `queue_position` 更像“当前排序位置”，不是绝对执行顺序

当前结合你的场景，更建议采用：

- **方案 B：资源可执行优先**

因为当前加载阶段的目标就是避免资源空转。  
但文档与实现都必须明确说明：

- `queued_loading` 允许非严格 FIFO 放行

避免后续实现者和前端同学按“严格排队”去理解。

## 8. `schedule.py` 的改造步骤

### 8.1 改造任务创建入口

当前 `POST /trigger` 的逻辑是：

- 发现同设备对已有运行任务，则排队
- 否则直接启动

建议改为：

1. 创建任务时先判断全局策略计算资源是否空闲
2. 若空闲：
   - 任务直接进入 `strategy`
   - `queue_status = running_strategy`
3. 若不空闲：
   - 任务进入 `queued_strategy`
   - `phase = strategy`
   - `message = 等待进入切分策略计算队列`

### 8.2 改造 `process_schedule_task`

建议将该函数拆成逻辑更清晰的三个部分：

1. `prepare_strategy_input`
   - 采集指标
   - 生成 `state_vector`
2. `run_strategy_stage`
   - 请求算法模块
   - 等待策略回调
3. `try_enter_loading_stage`
   - 判断加载资源是否空闲
   - 决定直接加载还是进入 `queued_loading`

### 8.3 改造策略计算完成后的推进逻辑

当前策略算完后直接进入 runtime 下发。

建议改为：

1. 策略计算成功
2. 立即释放“全局策略计算资源”
3. 立即推进下一个 `queued_strategy`
4. 当前任务再尝试进入加载阶段

这样能保证：

- 策略阶段串行
- 但不会因为当前任务等待加载而阻塞后续策略计算

这里还需要补一个实现约束：

- “释放策略资源 + 推进下一个策略任务”应视为同一轮调度动作

避免出现：

- 策略资源已释放
- 但下一个策略任务尚未被标记为 `running_strategy`
- 新触发任务又抢先占用了策略资源

### 8.4 改造加载失败 / 完成后的推进逻辑

当前完成或失败后是推进同设备对队列。

建议改为：

1. 释放当前任务占用的边端加载资源
2. 释放当前任务占用的云端加载资源
3. 在 `queued_loading` 中寻找下一条可执行任务
4. 若找到则开始加载

同时：

5. 若策略队列中有等待任务，也应继续由策略阶段的推进逻辑单独负责

同时必须补一条：

- 加载阶段的推进采用“资源可执行优先”还是“严格 FIFO”

当前文档建议采用：

- 资源可执行优先

即：

- 扫描 `queued_loading`
- 找到第一条边端与云端资源同时空闲的任务
- 立即放行

## 9. `queue_len` 的修改建议

### 9.1 当前不建议继续沿用旧语义

当前：

- `edge.metrics.queue_len`
- `cloud.metrics.queue_len`

表示的是设备对队列长度。

新方案下，这个值已经不再合理。

### 9.2 当前阶段的保守方案

建议先采用保守方案：

- 先不把 `queue_len` 作为真实设备指标使用
- 本次改造中统一固定为 `0.0`

避免在本次并发控制改造中，再把算法模块的输入语义同时打乱。

### 9.3 如果要同步调整

如果希望一起调整，建议改成更明确的值，例如：

- `strategy_queue_len`
  - 当前策略阶段等待任务数
- `loading_queue_len`
  - 当前针对该设备的加载等待数

但这会影响算法模块对字段语义的理解，因此不建议和本次主改造绑在一起。

### 9.4 当前实施结论

为了避免歧义，本次代码改造阶段直接约定：

- `edge.metrics.queue_len = 0.0`
- `cloud.metrics.queue_len = 0.0`

也就是说：

- 本次改造不再继续发送“设备对排队长度”
- 也暂不发送新的资源队列长度

等待后续与算法模块单独对齐后，再决定是否重新启用真实语义。

## 10. 推荐实施顺序

### 第一阶段：重构内部排队服务

目标：

- 先把设备对排队函数替换成二阶段资源函数

建议完成：

- 策略阶段资源判断函数
- 加载阶段资源判断函数
- 双阶段队列位置重算函数

### 第二阶段：改造 `/trigger`

目标：

- 新任务不再按设备对放行
- 改为按全局策略资源放行

建议完成：

- 新任务进入 `queued_strategy` 或 `strategy`
- 新文案与新 `queue_status`

### 第三阶段：改造 `process_schedule_task`

目标：

- 策略阶段与加载阶段彻底拆开

建议完成：

- 策略完成后释放策略资源
- 策略完成后推进下一个策略任务
- 当前任务再进入加载判断

### 第四阶段：改造加载完成 / 失败后的自动推进

目标：

- 加载阶段按真实资源推进，而不是按设备对推进

建议完成：

- `promote_next_loading_task`
- 对应状态与文案更新

### 第四点五阶段：补启动恢复与异常回收

目标：

- 避免因为服务重启、超时、回调丢失导致资源永久卡死

建议完成：

1. 应用启动时扫描 `schedule_tasks`
   - 对遗留的 `running_strategy`
   - 对遗留的 `running_loading`
   - 做统一状态修复
2. 对策略阶段保留明确超时回收
   - 超时后释放策略资源
   - 推进下一个策略任务
3. 对加载阶段增加兜底回收策略
   - 若长期未收到 runtime 回调
   - 应将任务标记失败
   - 并释放加载资源

### 第五阶段：联调验证

至少验证以下场景：

1. 两个任务同时进入，只有一个能进入策略计算
2. 第一个任务策略算完后，第二个任务能立即开始策略计算
3. 两个任务竞争同一个云端设备时，只能有一个进入加载
4. 不同边端但同一云端时，加载阶段仍然正确互斥
5. 任务失败后，下一个任务能自动推进
6. 服务重启后，不会遗留假占用资源
7. 策略超时或加载回调丢失后，资源能被正确释放

## 12. 当前建议结论

对于你当前的后端职责来说，最合适的代码改造路线是：

1. 先停止按设备对排队
2. 改为“全局策略计算串行”
3. 再改为“边云加载资源级排队”
4. 当前阶段任务完成点仍保持为“边云加载完成”
5. 先不把后续问答会话占用纳入本次实现

这样做的优点是：

- 更符合当前系统真实职责
- 不会过早引入下一阶段的会话占用复杂度
- 对现有外部模块的接口影响最小
- 后续若扩展到多云端实例，也更容易继续演进
